# What landed today

Three cards from four operators. Two sources, both from the agentic engineering lane. The week's signal concentrated here. Searches across PMM, AEO, iOS, game, and lifecycle email lanes found no qualifying mechanism-bearing claims published in the last seven days.

Both themes touch the same question: where does the agent system's structure come from, and who owns it when things go wrong?

## Agent topology at runtime

Anthropic's CJ Avilla and Harrison Stall presented Dynamic Workflows at AI Engineer New York on October 13, 2026. The Latent Space writeup landed October 12. Two cards came out of it.

`ins_avilla-dynamic-workflow-topology` captures the core design shift. In a standard multi-agent setup, the developer specifies a coordinator and subagent roster before work begins. In a dynamic workflow, the lead model receives the task, writes a coordination program, and determines the agent count and work distribution itself. Subagents share context through a filesystem but cannot message each other through the API directly, keeping each agent's context isolated and the topology explicit. Avilla stated the approach is "much more" expensive per session, but "much more effective at finding all of the details." The use case Avilla and Stall demonstrated: a stock watchlist scan where a scan phase assigned individual tickers to separate agents and a review phase synthesized the findings.

`ins_stall-budget-external-to-model` captures a design principle Stall named at the same talk. Telling a model its remaining token budget changes how it reasons. Stall:

> "a little bit anxious"

The practical consequence is that budget limits must be enforced by the harness, not disclosed inside the model's context. The model reasons at full capacity throughout; the harness terminates the session when the limit is reached. This is a behavioral observation from practitioners building production systems, not a controlled study. The principle applies beyond dynamic workflows to any long-running agentic session where reasoning quality matters throughout.

- CJ Avilla, `ins_avilla-dynamic-workflow-topology`. Dynamic workflows let the lead model design its own agent topology at runtime; the developer sets a budget, the model determines the structure.
- Harrison Stall, `ins_stall-budget-external-to-model`. Revealing a token budget to an agent model changes its reasoning behavior; enforce budgets externally to preserve output quality throughout the session.

## Infrastructure that survives the agent's process

Craig McLuckie and Joe Beda published on Latent Space on October 7, 2026, describing Mecatl, Stacklok's open-source agent harness. McLuckie and Beda co-created Kubernetes.

`ins_mcluckie-cloud-native-harness` captures their core structural argument. Desktop agent harnesses couple the agent loop, client, tools, credentials, and session state in a single process. When that process crashes or a container is evicted, the conversation ends. Containerizing that process moves the monolith without separating concerns. McLuckie:

> "Kubernetes taught this industry that a monolith in a container is still a monolith."

A cloud-native design externalizes state to durable storage and separates the engine from everything else. When a worker process dies, a replacement picks up from the last persisted turn boundary. Pod eviction becomes recoverable.

The governance argument is separate from the reliability argument. Agent interactions made on behalf of an enterprise are auditable only when the harness owns the session state. On a developer's laptop, that state belongs to the machine.

> "moving the locus of value from the desktop to the cloud"

Beda:

> "it's that much more difficult when it's sitting on a desktop"

Mecatl is early-stage. The claims rest on architectural reasoning from experienced distributed systems practitioners, not measured data from production deployments. Desktop harnesses remain the right tool for individual developers with short, bounded sessions.

The connection to this week's earlier cards is direct. Armin Ronacher's `ins_ronacher-codemode-harness-bash-limit` (October 6) described the brain-hands split at the process level: harness-native capabilities need a harness-native scripting layer because bash can only compose programs that run. McLuckie's argument applies the same concern one level up: harness-native reliability needs a harness-native infrastructure layer because a monolith container cannot separate concerns at the right boundaries.

- Craig McLuckie, `ins_mcluckie-cloud-native-harness`. Containerizing a desktop agent harness is not cloud-native; enterprise-grade session recovery and governance require purpose-built distributed architecture with durable external state.
