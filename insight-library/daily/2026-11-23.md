# What landed today

Three cards, no new operators. Harrison Chase published two posts this week on the structural problems teams hit when they move from simple task-based agents to production systems. Claire Vo published a case study on a fraud problem specific to AI products. The two threads are unrelated, but all three cards share a common shape: each names something that looks like a small extension of existing practice but requires a different system entirely.

## Theme 1, Goal-based agents are not bigger task-based agents

Harrison Chase published "From Tasks to Goals" on November 16. His core argument, documented in `ins_chase-goal-driven-agent-architecture`, is that the transition from handing an agent a task to handing it a goal is not a prompt change. It is an architecture change.

A task has a fixed scope and a natural end state. A goal is open-ended and persists until revoked. Chase identifies six architectural properties that goal-based agents require and task-based agents do not need: continuous task selection by the agent itself, finer-grained tool access controls, async clarification channels for when the user is absent, measurement and feedback mechanisms, explicit stopping rules and heartbeats, and persistent cross-run memory.

> "Giving an agent a goal isn't simply giving it a bigger prompt."

The stopping rules requirement is the most counterintuitive. Teams building goal-driven agents often assume the agent should always be doing something. Chase's point is the opposite:

> "Ongoing responsibility does not mean the agent should always find something to do."

An agent without a do-nothing path will generate noise by acting when new information does not warrant action. The result is repeated low-value touchpoints that make the agent feel unreliable even when it is technically functioning.

> "As agents become more powerful, we're moving from giving them tasks to giving them goals."

The card is `ins_chase-goal-driven-agent-architecture`. Six architectural properties, all structural, none addressable by prompt engineering alone.

## Theme 2, A knowledge factory closes the gap between agent execution and agent learning

Five days later, Chase published "How to Build a Knowledge Factory" on November 21. The post addresses a failure mode that teams hit after they deploy production agents: the knowledge the agent was given at launch goes stale, and the agent cannot fix it without creating contradictions.

The fix, documented in `ins_chase-knowledge-factory-curation-loop`, is a closed loop with two distinct roles. Executing agents flag knowledge gaps during runs. A separate curator agent reads those flags, plus raw sources and execution traces, and updates the knowledge store on a schedule. The boundary between execution and curation is explicit: an agent that updates its own instructions creates locally-scoped, potentially contradictory patches. A single curator writes consistent updates.

Chase identifies three knowledge categories the factory must maintain: skills (procedures), domain knowledge (slow-changing facts), and data-access guidance (which sources are authoritative and how to query them). Data-access guidance is the most neglected and the most consequential when it is wrong.

The recommended entry point: one recurring workflow, not comprehensive upfront documentation. Documentation written before agents run does not predict the gaps that surface in production. The gaps appear during execution, and the curator loop is what closes them continuously.

The card is `ins_chase-knowledge-factory-curation-loop`.

## Theme 3, AI products sell compute. The fraud model follows from that.

Claire Vo published a case study on November 16 about token fraud at ChatPRD. The post, documented in `ins_vo-ai-compute-not-seat-fraud`, opens with a premise that reframes the entire fraud problem for AI products:

> "If you sell AI, you sell compute."

Traditional SaaS fraud targets access to data or features. The product's cost of serving a fraudster is near-zero. AI product fraud works differently: the attacker gets authorized access, often via a free trial or promo code, and consumes inference budget at cost. Every fraudulent model call is a real line item on the AI provider's bill.

> "Count dollars, not requests."

The practical consequence: request-count rate limits do not stop this. A fraudster optimizing for maximum token consumption per request will stay under request-count thresholds while generating high costs. Dollar-based spend caps catch what request limits miss.

Vo identified six attack patterns at ChatPRD over approximately one year. Trial farming and card abuse exploit open access mechanisms. Relay traffic tunneling resells API access to third parties. MCP worker creation uses programmatic account setup for agents that consume compute continuously. When Vo probed one of these MCP workers, it stated:

> "I'm never sleeping."

Losses reached tens of thousands of dollars in inference costs. Stripe Radar detected $200,000 in attempted card-testing purchases. Vo cites the Stripe CEO's estimate that as many as 1 in 6 new signups to AI firms are fraudsters.

The operational response: shut off free trials, implement dollar-based spend caps per period, maintain a model allowlist in application code (not via API), block high-fraud-rate countries and IPs at the edge, and run hourly automated reviews of signup patterns with auto-bans at high confidence. A silent downgrade to cheaper models for suspected accounts reduces cost during the confidence accumulation period before a ban.

The card is `ins_vo-ai-compute-not-seat-fraud`.
