# What landed today

Three cards, no new operators. Two distinct clusters. Simon Willison releases the external sandbox pattern for coding agents on the Prime Radiant blog, an architectural answer to the question of how you trust an agent you cannot fully control. Dan Shipper and Swyx each name a different kind of reliability problem: Shipper on the feedback loop between human attention and AI learning, Swyx on the gap between prompt-chained LLMs and deterministic decision calls.

## Theme 1, Agent safety through architecture beats safety through model compliance

Willison's post, documented in `ins_willison-external-sandbox-pattern`, publishes three working implementations of a pattern he calls the external sandbox. The core idea inverts the usual trust structure: instead of hoping the agent follows rules, you place the code execution environment outside the agent's reach entirely. The agent runs on the host and sends commands to a localhost server; that server runs them inside a Linux VM with file system mounts and network access configured by the human before the session starts. No prompt injection can expand what the sandbox permits, because the sandbox does not obey the agent.

> "A sandbox is a protection that doesn't depend on any model's judgment."

The three implementations cover the main macOS and Linux host scenarios: v86 (WebAssembly, no container runtime required), Apple Containers, and QEMU via Microsoft's Quicksand library. Claude Code uses a shell prefix variable, Codex uses an exec-server protocol, and Pi uses a tool-replacement extension. Each routes all execution through the same localhost API surface. The credential-replacement feature, which lets the sandbox add API keys to outbound requests without putting them in the agent's context, closes a prompt-injection vector that most agent setups leave open.

- Simon Willison, `ins_willison-external-sandbox-pattern`. The external sandbox pattern makes coding agent safety a property of the execution environment, not of the model's compliance.

## Theme 2, The reliability gap in AI-native work has two distinct causes

Shipper and Swyx both describe how AI systems become unreliable. They work at different layers, but the structural logic is the same: speed at one point in the system does not substitute for quality at another.

Shipper's Nov 13 article, documented in `ins_shipper-attention-ai-formula`, names human attention as the bottleneck in AI feedback loops. His head of evals ran a Frontier experiment: Claude predicted Shipper's Slack replies correctly in 93% of 400 test cases but could not reliably rank which reply Shipper would actually send. Generation is solved; ranking is not. The fix is not better models. It is exchanges designed so that answering feels worthwhile. A good AI collaborator, like a skilled interviewer who has read your work first, asks questions that make you understand your own preferences better rather than asking you to grade outputs.

> "a question from an AI is only worth asking if you'll actually answer it"

Swyx's Nov 11 article, documented in `ins_swyx-system-one-call-embeds`, documents a different layer of the same problem: the step in a pipeline where text generation produces inconsistent results can be replaced with a structured decision call. System One models return a rank, a probability, or a category rather than text. Called like functions inside application code, they can run thousands of times in a single request (UiPath built a document ranking tournament completing in under a second). Workday used the same pattern to build a time-off card that fills in while the user is still typing. The underlying principle, stated by Diogo Almeida of TypeSafe AI: "code is the language of automation." Put decision logic in code, not in prompts.

The two cards do not converge on a single pattern, but they name the same structural move: speed at the generation step without quality at the selection or decision step produces unreliable systems.

- Dan Shipper, `ins_shipper-attention-ai-formula`. Human attention is the scarce input in AI feedback loops. The bottleneck is designing exchanges that make answering worthwhile.
- Swyx, `ins_swyx-system-one-call-embeds`. Non-generative System One decision models embedded as function calls in application code produce more reliable results than prompt-stitched LLM chains.
