# What landed today

Three cards from two operators. Tom Tunguz asks whether AI-era software is grown or designed. Lily Ray documents that Google's documentation pages are already answering that question for content teams, weeks before the algorithm acts on it.

## Two modes of building, not two philosophies in conflict

Tomasz Tunguz's October 2 essay does not argue that vibe coding is better or worse than formal design. It names both as legitimate modes in an AI-era development toolbox, each suited to a different correctness requirement.

`ins_tunguz-grow-or-design-modes` captures the core bifurcation. Vibe coding works like bacterial culture selection: run parallel experiments, keep the variant that survives, discard the rest. State machine design works like formal engineering: enumerate all possible states in a flowchart before writing a line of code, then verify all paths with tools like Lean or TLA+. The choice is not about preference. It is about whether the system needs to discover what is correct or prove it.

The Boris Cherny example inside the essay is notable. Cherny formally verified the Claude Agent SDK using Lean and TLA+, applying state machine design to agent harness infrastructure. That is the kind of system where every transition must be provably handled. An experimental UI feature is not.

Tunguz situates both modes inside a longer engineering history that includes TDD, pair programming, and "move fast and break things." Each era produced a default development mode that matched its dominant correctness criterion. The current era produces two defaults for two distinct task classes, not one.

- Tomasz Tunguz, `ins_tunguz-grow-or-design-modes`. Vibe coding discovers correctness by organic selection; state machine design proves it by enumerating every path. Both are valid AI-era modes.

## Google is already signaling the next wave before the algorithm moves

Lily Ray's October 4 post is structured as a prediction. The argument is a pattern-match: seven specific changes in Google's documentation match what happened before Panda (2011), Penguin (2012), and the March 2024 core update. The updates followed. The documentation changes came first.

`ins_lily-ray-google-doc-change-early-warning` documents the 2026 cluster: AI content guidance that now calls manual fact-checking "critical," a redefined "main content" criterion requiring effort, originality, and talent, and explicit identification of AI-generated headshots and invented credentials as deceptive. Glenn Gabe, Marie Haynes, and Cyrus Shepard independently reached the same conclusion from the same signals. Ray's framework is a checklist, not a prediction from theory. It is a recognition of a pattern that has already repeated across three major update cycles.

The second card, `ins_lily-ray-scaled-content-top-enforcement`, captures what Google is actually targeting. Gary Illyes stated directly at Search Central Live Barcelona that scaled content is now

> "becoming more of a problem than link spam."

Four spam updates in 2026, with the interval between them shrinking from 92 days to 37 days, confirm the acceleration. This is not a shift in what Google penalizes. It is a shift in which violation class gets the most enforcement effort. Link spam still violates guidelines. Scaled low-effort AI content is now the higher-volume, higher-priority threat.

The two Lily Ray cards are related but distinct. The first tells practitioners how to see an update coming. The second tells them what the update will target when it arrives.

- Lily Ray, `ins_lily-ray-google-doc-change-early-warning`. Seven observable Google documentation changes in October 2026 match the pre-update pattern from Panda, Penguin, and March 2024.
- Lily Ray, `ins_lily-ray-scaled-content-top-enforcement`. Scaled AI-generated content has displaced link spam as Google's primary enforcement target, per Gary Illyes and four 2026 spam updates.
